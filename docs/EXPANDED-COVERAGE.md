# Coverage added in 2.1.0

Research and live spot checks: **24 October 2026**. This release adds 15 adapters to the existing 19, for **34 provider UI adapters**. Multiple generations of a library can have separate adapters. These numbers describe maintained interfaces, not a measured percentage of websites or a guarantee that every vendor configuration works.

## New adapters and primary evidence

Selectors were independently written after tracing the actual upstream refusal handlers. Only UI signatures and action semantics are used; vendor implementations and third-party automatic-consent rule collections are not bundled.

## Recognition improvements across custom websites

- Consent context can use a dialog's bounded `aria-label` or `aria-labelledby`, in addition to visible text. It still requires cookie/tracking vocabulary and a technical consent context; a medical or payment-consent dialog cannot qualify on the word “consent” alone.
- Native associated labels can name action controls, including input buttons. Conflicting acceptance/refusal names are rejected. Labels are indexed once per root per sweep to avoid repeatedly scanning large forms. [W3C accessible naming guidance](https://www.w3.org/WAI/ARIA/apg/practices/names-and-descriptions/) and [native label association](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/labels) explain those naming mechanisms.
- Standard alert banners are recognized, including the relative-position banner in [Microsoft's consent-banner implementation](https://github.com/microsoft/consent-banner/blob/8a654a8920a4b9813a9cc2d99c08f8bc1eb59a4c/src/index.ts). Exact rejection wording is still required by generic matching; no hashed styling class or button position is used as an action.
- Known CMP wrappers and named dialogs with `display:contents`, zero height, or fixed descendants can be recognized through their visible controls. Every ancestor, including shadow hosts, is still checked for hidden/inert state before acting.
- Unicode hyphens and discretionary soft hyphens normalize consistently. Additional exact refusal phrases include “No, thanks”, “Accept only essential cookies”, and “Continue without consenting”. Mixed instructions such as “Reject all — accept analytics” remain unmatched. Arbitrary punctuation, suffixes or subscription conditions are not stripped to manufacture a match.

## Validation

The real unpacked MV3 extension is exercised in isolated Chromium profiles against controlled fixtures. New tests force provider selectors by replacing refusal text with an unlisted translation, retain acceptance decoys, and cover modern Sourcepoint metadata, custom callback/subscription traps, the Cookie Information shared-class trap, multi-step settings, closed shadow roots, accessible labels, hidden ancestors, and unrelated food/purchase/medical popups. Fixtures verify routing and safety; they do not execute a vendor's production consent backend.

Live spot checks in an English/UK desktop session on 24 October 2026:

| Site/interface | Observed outcome |
| --- | --- |
| [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/) | The WCP banner disappeared and `MSCC` recorded `c1=1`, `c2=1`, `c3=1`. The inspected [official WCP runtime](https://wcpstatic.microsoft.com/mscc/lib/v2/wcp-consent.js) defines 1 as Rejected and 2 as Accepted. |
| [CookieScript homepage](https://cookie-script.com/) | The extension clicked `cookiescript_reject` (“Decline all”); the banner disappeared and the settings badge remained. |
| [Orejime demo](https://orejime.boscop.fr/) | The extension clicked the Banner decline button in the embedded `features/purposes.html` frame; the consent controls disappeared. |
| [Civic product site](https://cookiecontrol.com/) | The notification's `ccc-notify-reject` (“I Do Not Accept”) was clicked and the notification disappeared. |
| [Termly homepage](https://termly.io/) | The live banner's Decline control was clicked and the banner disappeared. |
| [The Guardian](https://www.theguardian.com/uk) | Its Sourcepoint interface offered “Reject all and subscribe” using custom JavaScript choice type 9. The extension left this paid/conditional choice untouched. This is an intentional boundary, not a successful rejection. |

The GlowCookies GitHub Pages demo candidate returned 404, so no live success is claimed there. Live checks are observations of those sessions, not a representative web benchmark or proof that all subsequent tracking stopped. Cookies already set, noncompliant tracking, paywalls, unsupported regional variants and browser-restricted pages remain outside the guarantee.
